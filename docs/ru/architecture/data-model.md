# Модель данных

## 1. Назначение

Этот документ определяет планируемую реляционную модель данных для MVP
Mini E-commerce.

Модель должна поддерживать:

- Каталог товаров.
- Не более одной корзины на пользователя, создаваемой при первом обращении к
  корзине.
- Позиции корзины с проверенными количествами.
- Заказы с неизменяемыми снимками покупки.
- Списание и восстановление запаса.
- Идемпотентность оформления заказа.
- Транзакционную согласованность при одновременных запросах.

SQL Server — целевая реляционная база данных, а Entity Framework Core —
технология сохранения данных по умолчанию.

Этот документ определяет предполагаемую модель и её требования к целостности.
Точные конфигурации EF Core и миграции будут реализованы на этапе
инфраструктуры.

## 2. Принципы проектирования

1. Используйте реляционные ограничения для защиты целостности данных везде, где
   это практически возможно.
2. Представляйте денежные значения с помощью SQL Server `decimal(18,2)`.
3. Храните метки времени в UTC.
4. Используйте первичные и внешние ключи для связей между сущностями.
5. Избегайте физического удаления товаров, на которые ссылаются корзины или
   исторические заказы.
6. Храните названия товаров и цены на момент покупки в позициях заказа.
7. Сохраняйте атомарность операций оформления заказа и отмены.
8. Используйте механизмы конкурентного доступа, специфичные для SQL Server, где
   это требуется.
9. Не рассматривайте валидацию на уровне приложения как замену транзакционным
   операциям базы данных.
10. Не добавляйте таблицы для функций за пределами MVP.

## 3. Обзор сущностей

Планируемые сохраняемые сущности:

- `User`
- `Product`
- `Cart`
- `CartItem`
- `Order`
- `OrderItem`
- `CheckoutAttempt`

Эти имена — логические имена сущностей. Точные имена таблиц и соглашения об
именовании могут быть окончательно определены при настройке EF Core.

## 4. Определения сущностей

### 4.1 Пользователь

Представляет идентичность клиента, известную приложению.

| Свойство | Предлагаемый тип SQL | Требования |
|---|---|---|
| `Id` | `uniqueidentifier` | Первичный ключ |
| `Email` | `nvarchar(320)` | Обязательно; уникально |
| `CreatedAtUtc` | `datetime2` | Обязательно; UTC |

Требования:

- У каждого пользователя есть стабильный идентификатор.
- Уникальность адреса электронной почты должна обеспечиваться базой данных.
- Начальные данные для Development должны быть повторяемыми и не создавать
  дублирующихся пользователей.
- Идентичность пользователя, используемая для принадлежности корзины и заказа,
  берётся из контекста аутентифицированного запроса.
- MVP не требует регистрации клиентов или хранения паролей.

Сущность `User` представляет идентичность клиента приложения. Это не означает,
что в MVP реализуется полноценная система управления идентификацией.

### 4.2 Товар

Представляет товар каталога и его текущее состояние запаса.

| Свойство | Предлагаемый тип SQL | Требования |
|---|---|---|
| `Id` | `uniqueidentifier` | Первичный ключ |
| `Name` | `nvarchar(200)` | Обязательно |
| `Description` | `nvarchar(max)` | Обязательно, если окончательный контракт не допускает null |
| `Price` | `decimal(18,2)` | Обязательно; неотрицательно |
| `StockQuantity` | `int` | Обязательно; неотрицательно |
| `IsActive` | `bit` | Обязательно |
| `CreatedAtUtc` | `datetime2` | Обязательно; UTC |

Требования:

- В публичном каталоге отображаются только активные товары.
- Товары деактивируются с помощью `IsActive = false`; физическое удаление не
  входит в MVP.
- Запас не может быть отрицательным.
- Цена должна быть неотрицательной.
- При создании заказа оформление заказа использует текущую цену товара.
- Списания запаса должны быть атомарными и выполняться только при достаточном
  запасе.

Ограничение CHECK базы данных должно обеспечивать неотрицательность запаса и
цены.

Если при окончательном определении контракта выбирается возможность null для
описаний, сопоставление базы данных и DTO API должны быть согласованы.

### 4.3 Корзина

Представляет сохраняемую корзину покупок пользователя.

| Свойство | Предлагаемый тип SQL | Требования |
|---|---|---|
| `Id` | `uniqueidentifier` | Первичный ключ |
| `UserId` | `uniqueidentifier` | Обязательно; внешний ключ на `User` |
| `RowVersion` | `rowversion` | Обязательный токен конкурентности |
| `CreatedAtUtc` | `datetime2` | Обязательно; UTC |
| `UpdatedAtUtc` | `datetime2` | Обязательно; UTC |

Требования:

- У пользователя не более одной корзины.
- Корзина сохраняется, даже если не содержит позиций.
- Корзина создаётся при первом обращении пользователя через `GET /api/cart`.
- Успешное оформление заказа удаляет позиции корзины, но сохраняет запись
  корзины.
- Уникальное ограничение на `UserId` обеспечивает правило одной корзины на
  пользователя и разрешает одновременные первые создания: проигравшая вставка
  завершается ошибкой ограничения, а реализация повторно читает выигравшую
  строку.
- `RowVersion` используется как часть стратегии защиты от устаревших обновлений
  и предоставляется клиентам как `ETag` корзины.
- Успешное оформление заказа должно обновлять строку корзины, например
  устанавливая `UpdatedAtUtc`, в той же транзакции. Это гарантирует изменение
  `rowversion` и недействительность ранее выданного `ETag`.

SQL Server автоматически создаёт и обновляет значение `rowversion`. Код
приложения не должен присваивать его вручную.

Изменения корзины и оформление заказа требуют, чтобы клиент передал текущий
`ETag` через `If-Match`. Устаревшие значения отклоняются с
`412 Precondition Failed`, а отсутствие обязательного `If-Match` — с
`428 Precondition Required`.

### 4.4 Позиция корзины

Представляет товар и количество, которые сейчас находятся в корзине.

| Свойство | Предлагаемый тип SQL | Требования |
|---|---|---|
| `Id` | `uniqueidentifier` | Первичный ключ |
| `CartId` | `uniqueidentifier` | Обязательно; внешний ключ на `Cart` |
| `ProductId` | `uniqueidentifier` | Обязательно; внешний ключ на `Product` |
| `Quantity` | `int` | Обязательно; больше нуля |
| `CreatedAtUtc` | `datetime2` | Обязательно; UTC |
| `UpdatedAtUtc` | `datetime2` | Обязательно; UTC |

Требования:

- Корзина не может содержать несколько строк для одного товара.
- Уникальное ограничение на `(CartId, ProductId)` обеспечивает это правило.
- Количество должно быть положительным.
- Добавление уже присутствующего в корзине товара увеличивает его существующее
  количество.
- Операции с корзиной должны проверять активность товара и запас в соответствии
  со спецификацией.
- Деактивация товара не удаляет автоматически его существующую позицию корзины.
- Позиции корзины удаляются явным удалением или успешным оформлением заказа.

Ограничение CHECK базы данных должно обеспечивать `Quantity > 0`.

Ссылка позиции корзины на товар сохраняется для навигации и проверки. Позиция
корзины не является снимком покупки: её отображаемая цена берётся из текущих
данных каталога в соответствии с утверждёнными бизнес-правилами.

### 4.5 Заказ

Представляет успешно завершённое оформление заказа.

| Свойство | Предлагаемый тип SQL | Требования |
|---|---|---|
| `Id` | `uniqueidentifier` | Первичный ключ |
| `UserId` | `uniqueidentifier` | Обязательно; внешний ключ на `User` |
| `Status` | `nvarchar(20)` | Обязательно; `Created` или `Cancelled` |
| `CreatedAtUtc` | `datetime2` | Обязательно; UTC |
| `TotalAmount` | `decimal(18,2)` | Обязательно; неотрицательно |

Поддерживаемые статусы в MVP:

- `Created`
- `Cancelled`

Требования:

- Заказ принадлежит одному пользователю.
- Создание заказа и списание запаса происходят в одной транзакции оформления
  заказа.
- Заказ содержит одну или более позиций заказа.
- Общая сумма заказа рассчитывается по сохранённым ценам за единицу и
  количествам позиций заказа.
- Исторические данные заказа должны оставаться независимыми от последующих
  изменений цен каталога или названий товаров.
- Отмена изменяет статус заказа и атомарно восстанавливает запас.
- Заказы не удаляются физически в рамках MVP.

Ограничение CHECK должно обеспечивать неотрицательность сумм и ограничивать
`Status` поддерживаемым набором.

### 4.6 Позиция заказа

Представляет строку заказа и сохраняет снимок на момент покупки.

| Свойство | Предлагаемый тип SQL | Требования |
|---|---|---|
| `Id` | `uniqueidentifier` | Первичный ключ |
| `OrderId` | `uniqueidentifier` | Обязательно; внешний ключ на `Order` |
| `ProductId` | `uniqueidentifier` | Обязательно; внешний ключ на `Product` |
| `ProductName` | `nvarchar(200)` | Обязательно; снимок |
| `UnitPrice` | `decimal(18,2)` | Обязательно; снимок |
| `Quantity` | `int` | Обязательно; положительное |

Требования:

- `ProductName` копируется из товара при создании заказа в ходе оформления.
- `UnitPrice` копируется из текущей цены каталога во время оформления заказа.
- `Quantity` копируется из проверенного количества в корзине.
- Сумма строки равна `UnitPrice × Quantity`.
- Общая сумма заказа — сумма всех сумм строк.
- Последующие переименования товаров или изменения цен не должны изменять
  исторические данные заказа.
- Отмена восстанавливает точные количества, записанные в позициях заказа.

Ограничение CHECK должно обеспечивать `Quantity > 0` и неотрицательность
`UnitPrice`.

`ProductId` остаётся ссылкой на товар каталога, а `ProductName` и `UnitPrice`
сохраняют исторические сведения о покупке.

Товары нельзя физически удалять, пока на них ссылаются позиции заказа.

### 4.7 Попытка оформления заказа

Представляет идемпотентную попытку оформления заказа.

| Свойство | Предлагаемый тип SQL | Требования |
|---|---|---|
| `Id` | `uniqueidentifier` | Первичный ключ |
| `UserId` | `uniqueidentifier` | Обязательно; внешний ключ на `User` |
| `IdempotencyKey` | `nvarchar(128)` | Обязательно; должен соответствовать формату ключа, определённому в `../DECISIONS.md` |
| `RequestFingerprint` | `varbinary(32)` | Обязательно; SHA-256 целевого запроса и переданного значения `If-Match` |
| `Status` | `nvarchar(20)` | Обязательно; `InProgress` или `Completed` |
| `OrderId` | `uniqueidentifier` | Внешний ключ на `Order`; допускает null |
| `ResponseStatusCode` | `int` | Допускает null, пока не записан окончательный результат |
| `ResponsePayload` | `nvarchar(max)` | Допускает null, пока не записан окончательный результат |
| `LeaseExpiresAtUtc` | `datetime2` | Обязательно; используется при восстановлении по требованию |
| `CreatedAtUtc` | `datetime2` | Обязательно; UTC |
| `UpdatedAtUtc` | `datetime2` | Обязательно; UTC |

Требования:

- Ключ идемпотентности действует в пределах одного пользователя.
- Уникальное ограничение на `(UserId, IdempotencyKey)` предотвращает
  дублирующиеся попытки для одного пользователя и ключа и определяет, какое
  одновременное резервирование побеждает.
- Отпечаток запроса представляет семантически значимое содержимое запроса,
  определённое в `../adr/ADR-002-checkout-idempotency.md`.
- Повторное использование одного и того же ключа с другим отпечатком запроса
  приводит к `409 Conflict` с кодом `idempotency_key_reused`.
- Повторение одного и того же ключа и отпечатка возвращает сохранённый результат,
  если он существует.
- Успешная попытка связывается с созданным заказом.
- `ResponseStatusCode` и `ResponsePayload` хранят ответ, который должен быть
  воспроизведён, включая окончательные ответы об ошибках бизнес-правил.
- Неожиданные внутренние ошибки не должны записываться как окончательные
  бизнес-результаты; запись остаётся в состоянии `InProgress`.
- Восстановление не должно слепо выполнять попытку, устойчивый результат которой
  неизвестен.

Модель состояний:

- `InProgress` — попытка зарезервирована и не имеет устойчивого окончательного
  результата. `ResponseStatusCode` и `ResponsePayload` равны null.
- `Completed` — окончательный ответ сохранён и должен быть воспроизведён.
  `Completed` охватывает как успешные оформления заказа, так и окончательные
  ошибки бизнес-правил; сохранённый код состояния различает их.

Переходы:

- Вставка со статусом `InProgress` при резервировании ключа, при этом
  `LeaseExpiresAtUtc` устанавливается равным текущему времени UTC плюс срок
  резервирования.
- `InProgress` → `Completed` внутри успешной транзакции оформления заказа вместе
  с изменениями заказа, запаса и корзины.
- `InProgress` → `Completed` в отдельной транзакции после отката неудачной
  транзакции оформления заказа с сохранением окончательного ответа об ошибке
  бизнес-правила.
- `InProgress` остаётся `InProgress` после инфраструктурной ошибки или
  неизвестного результата фиксации.

Восстановление по требованию захватывает истёкшую попытку условным обновлением,
которое выполняется успешно, только когда запись всё ещё находится в состоянии
`InProgress`, а `LeaseExpiresAtUtc` находится в прошлом. Продолжает только
запрос, затрагивающий одну строку; все остальные следуют политике ожидания
выполняющейся попытки. Захват продлевает `LeaseExpiresAtUtc` на время попытки
восстановления.

Записи не очищаются автоматически в MVP, как определено в `../DECISIONS.md`.

## 5. Связи

Предполагаемые связи:

```text
User 1 ─── 0..1 Cart
Cart 1 ─── 0..* CartItem
Product 1 ─── 0..* CartItem

User 1 ─── 0..* Order
Order 1 ─── 1..* OrderItem
Product 1 ─── 0..* OrderItem

User 1 ─── 0..* CheckoutAttempt
Order 1 ─── 0..* CheckoutAttempt
```

Связь `Order` с `CheckoutAttempt` необязательна со стороны попытки, поскольку
оформление заказа может завершиться неудачно до создания заказа.

Уникальность `Cart.UserId` обеспечивает не более одной корзины на пользователя.
Строка корзины создаётся при первом обращении пользователя к корзине через
`GET /api/cart`; никакая другая операция её не создаёт.

## 6. Ограничения и индексы

Схема базы данных должна обеспечивать следующие ограничения.

| Сущность | Ограничение | Назначение |
|---|---|---|
| `User` | Уникальность `Email` | Предотвращать дублирование идентичностей клиентов |
| `Product` | `Price >= 0` | Не допускать отрицательных цен |
| `Product` | `StockQuantity >= 0` | Не допускать отрицательного запаса |
| `Cart` | Уникальность `UserId` | Одна корзина на пользователя |
| `CartItem` | Уникальность `(CartId, ProductId)` | Одна строка на товар в корзине |
| `CartItem` | `Quantity > 0` | Не допускать недопустимых количеств |
| `Order` | `TotalAmount >= 0` | Не допускать отрицательных сумм заказа |
| `Order` | `Status IN ('Created', 'Cancelled')` | Ограничивать статусы поддерживаемым набором |
| `OrderItem` | `Quantity > 0` | Не допускать недопустимых количеств в заказе |
| `OrderItem` | `UnitPrice >= 0` | Не допускать отрицательных цен покупки |
| `CheckoutAttempt` | Уникальность `(UserId, IdempotencyKey)` | Предотвращать дублирующиеся попытки идемпотентности |
| `CheckoutAttempt` | `Status IN ('InProgress', 'Completed')` | Ограничивать состояния поддерживаемым набором |
| `CheckoutAttempt` | `LeaseExpiresAtUtc IS NOT NULL` | Поддерживать восстановление по требованию |

Внешние ключи должны защищать предполагаемые связи.

Дополнительные индексы должны поддерживать типичные запросы:

- Запросы активного каталога товаров.
- Поиск корзины по пользователю.
- Поиск позиций корзины по корзине.
- Поиск истории заказов по пользователю и времени создания.
- Поиск позиций заказа по заказу.
- Поиск идемпотентности по пользователю и ключу.

Точный порядок индексов и дополнительные включённые столбцы следует выбирать на
основе финальных шаблонов запросов. Не добавляйте предположительные индексы без
явной необходимости.

## 7. Удаление и ссылочная целостность

Физическое удаление товаров не поддерживается в MVP.

Рекомендуемое поведение:

- Деактивируйте товары с помощью `IsActive = false`.
- Сохраняйте записи товаров, на которые ссылаются позиции корзины или позиции
  заказа.
- Удаляйте позиции корзины явно или во время успешного оформления заказа.
- Сохраняйте записи заказов и позиций заказа после отмены.
- Сохраняйте записи идемпотентности в течение срока, требуемого утверждённой
  политикой повторных попыток и восстановления.

Каскадное удаление не должно случайно удалять исторические заказы, снимки
покупок или результаты идемпотентности.

Любое настроенное каскадное поведение должно явно проверяться в сопоставлениях
EF Core.

## 8. Денежные значения и расчёты заказа

Все денежные значения используют USD и SQL Server `decimal(18,2)`.

Для каждой позиции заказа:

`LineTotal = UnitPrice × Quantity`

Для заказа:

`TotalAmount = SUM(LineTotal)`

Требования:

- Используйте десятичную арифметику, а не типы с плавающей запятой, для денежных
  значений.
- Рассчитывайте общую сумму заказа по ценам за единицу и количествам на момент
  покупки.
- Сохраняйте полученную общую сумму заказа при создании заказа.
- Не применяйте налоги, стоимость доставки, купоны, скидки или конвертацию валют
  в MVP.
- Проверяйте числовые границы, чтобы вычисление не переполняло молча
  поддерживаемую точность базы данных.

Точное представление на уровне приложения и числовые границы должны
соответствовать контракту API и схеме базы данных.

## 9. Транзакционные инварианты

### 9.1 Оформление заказа

Успешное оформление заказа должно атомарно:

1. Проверить текущую корзину в соответствии с утверждённой стратегией блокировки
   корзины, включая переданное значение `If-Match`.
2. Проверить активность товаров и запрошенные количества.
3. Списать запас с помощью атомарных условных обновлений.
4. Создать заказ и снимки позиций заказа, читая названия товаров и цены, пока
   строки товаров заблокированы.
5. Очистить позиции корзины.
6. Обновить строку корзины так, чтобы изменился её `rowversion`.
7. Записать завершённый результат идемпотентности согласованно с заказом.

Если какое-либо требуемое списание запаса завершается неудачно, транзакция
оформления заказа должна откатить все бизнес-изменения.

Резервирование идемпотентности может фиксироваться отдельно в соответствии с
утверждённой гибридной стратегией. Это резервирование не должно приводить к
частичному заказу или частичному списанию запаса.

### 9.2 Отмена

Отмена должна атомарно:

1. Проверить принадлежность.
2. Перевести заказ в состояние `Cancelled` условным обновлением, которое
   выполняется успешно, только когда заказ всё ещё находится в состоянии
   `Created`.
3. Восстановить количества, записанные в позициях заказа, обрабатывая строки
   товаров в стабильном порядке.

Восстанавливать запас может только запрос, переход статуса которого затрагивает
одну строку. Одновременные попытки отмены не должны восстанавливать одни и те же
количества более одного раза; проигравшие попытки получают `409 Conflict`.

### 9.3 Конкурентный доступ к корзине

Изменения корзины и оформление заказа должны следовать утверждённой стратегии
блокировки.

`rowversion` — это токен конкурентности, а не замена явному механизму блокировки
корзины. Клиенты передают его через `If-Match`; устаревшие значения отклоняются
с `412 Precondition Failed`, а отсутствие обязательного `If-Match` — с
`428 Precondition Required`.

Строка корзины должна обновляться при каждом изменении содержимого корзины, в
том числе во время оформления заказа, чтобы `rowversion` всегда отражал
логическое состояние корзины.

## 10. Рекомендации по сопоставлению EF Core

- Используйте явные конфигурации сущностей, когда они делают реляционные
  ограничения и поведение проще для проверки.
- Настраивайте точность десятичных значений явно.
- Настраивайте `RowVersion` с использованием поддержки rowversion в SQL Server.
- Настраивайте внешние ключи, уникальные индексы и ограничения CHECK явно.
- Используйте миграции для развития схемы.
- Не полагайтесь только на соглашения EF Core для критически важных требований
  уникальности, точности или конкурентного доступа.
- Сохраняйте видимой и тестируемой логику блокировок и условных обновлений,
  специфичную для SQL Server.
- Не используйте поставщик EF Core в памяти для утверждений о корректности
  блокировок SQL Server или поведения транзакций.

## 11. Оставшиеся детали

Решения, влияющие на схему, зафиксированы в `../DECISIONS.md`,
`../adr/ADR-001-cart-concurrency.md` и
`../adr/ADR-002-checkout-idempotency.md`: создание корзины при первом обращении,
обработка `If-Match` и `rowversion`, модель состояний попытки оформления заказа,
формат ключа, алгоритм отпечатка и поля срока резервирования.

Следующие детали реализации остаются открытыми и не влияют на контракт:

- Точная допустимость null и максимальные длины для необязательных полей товара.
- Окончательный список индексов, выбранный по измеренным шаблонам запросов.
- Точное представление сохраняемого тела ответа при условии, что оно
  воспроизводит задокументированный ответ.

Не придумывайте детали, которые изменили бы совместимость API, безопасность
транзакций или корректность восстановления.
