# Архитектура бэкенда

## 1. Назначение

Этот документ определяет архитектуру бэкенда MVP Mini E-commerce.

Бэкенд следует принципам Clean Architecture и разделяет бизнес-правила,
прикладные сценарии использования, инфраструктурные задачи и
HTTP-представление.

Архитектура должна оставаться понятной для проекта, который разрабатывает один
разработчик. Она не должна вводить абстракции или слои без конкретной
необходимости.

## 2. Структура решения

Бэкенд расположен в `src/Backend/PS.MiniEcommerce/`. Файл решения —
`src/Backend/PS.MiniEcommerce/PS.MiniEcommerce.slnx`; используется формат
`.slnx`.

Бэкенд состоит из четырёх проектов:

```text
src/Backend/PS.MiniEcommerce/
├── PS.MiniEcommerce.slnx
├── PS.MiniEcommerce.Domain/
├── PS.MiniEcommerce.Application/
├── PS.MiniEcommerce.Infrastructure/
└── PS.MiniEcommerce.API/
```

Автоматизированные тесты поддерживаются отдельно:

```text
tests/
├── PS.MiniEcommerce.UnitTests/
└── PS.MiniEcommerce.IntegrationTests/
```

Префикс `PS.` является частью согласованного именования и сохраняется в именах
проектов, пространствах имён и путях (см. `../DECISIONS.md`, раздел 1.1).

### 2.1 PS.MiniEcommerce.Domain

Содержит основную бизнес-модель и бизнес-инварианты.

Обязанности:

- Доменные сущности и объекты-значения там, где это обосновано.
- Определения статусов заказа и корзины.
- Бизнес-правила, независимые от HTTP, EF Core и инфраструктуры.
- Специфичные для предметной области типы и исключения, если они приносят
  очевидную пользу.

Проект Domain не должен зависеть от Application, Infrastructure или API.

Он не должен содержать:

- EF Core `DbContext` или конфигурации сохранения данных.
- HTTP-контроллеры или DTO запросов.
- Обработчики MediatR.
- SQL-запросы.
- Интеграции с внешними сервисами.

Сохраняйте доменную модель прагматичной. Не вводите систему доменных событий,
фреймворк агрегатов или сложные доменные сервисы без подтверждённой
потребности.

### 2.2 PS.MiniEcommerce.Application

Содержит сценарии использования и оркестрацию на уровне приложения.

Обязанности:

- Команды и запросы MediatR.
- Обработчики команд и запросов.
- DTO запросов и ответов приложения там, где это уместно.
- Валидаторы FluentValidation.
- Поведения конвейера.
- Интерфейсы, необходимые прикладным сценариям использования.
- Абстракция текущего пользователя.
- Оркестрация транзакционных бизнес-операций через соответствующие интерфейсы.

Примеры сценариев использования:

- Получение активных товаров.
- Получение сведений о товаре.
- Получение корзины текущего пользователя.
- Добавление или обновление позиции корзины.
- Удаление позиции корзины.
- Оформление заказа.
- Получение истории заказов и сведений о заказе.
- Отмена заказа.

Application зависит от Domain, но не должен зависеть от Infrastructure или API.

MediatR используется на границе приложения для диспетчеризации команд и
запросов. Не используйте его как универсальную шину событий.

### 2.3 PS.MiniEcommerce.Infrastructure

Реализует сохранение данных и поведение, специфичное для инфраструктуры.

Обязанности:

- EF Core `DbContext`.
- Конфигурации сущностей и сопоставления с базой данных.
- Миграции EF Core.
- Абстракции репозиториев или сохранения данных только там, где это обосновано.
- Блокировки и условные обновления запаса, специфичные для SQL Server.
- Реализации интерфейсов, определённых в Application.
- Инициализация базы данных и начальные данные для Development.
- Обработка транзакций, специфичная для инфраструктуры.

Infrastructure зависит от Application и Domain.

Требования корректности, специфичные для SQL Server, должны реализовываться
явно. Нельзя предполагать, что одного EF Core LINQ достаточно для генерации
требуемых подсказок блокировки.

Избегайте дублирования прикладных бизнес-процессов в Infrastructure.
Infrastructure должна реализовывать операции сохранения данных и механизмы базы
данных, необходимые для соблюдения согласованных инвариантов.

### 2.4 PS.MiniEcommerce.API

Проект API — это слой HTTP-представления.

Обязанности:

- Контроллеры ASP.NET Core.
- Контракты HTTP-запросов и ответов там, где это уместно.
- Конфигурация аутентификации и авторизации.
- Тестовая аутентификация только для Development.
- Сопоставление кодов состояния HTTP.
- Ответы об ошибках в формате `ProblemDetails`.
- Композиция внедрения зависимостей.
- Промежуточное ПО и конфигурация запуска приложения.

Контроллеры должны оставаться тонкими.

Контроллер должен:

1. Принять HTTP-запрос.
2. Полагаться на привязку и валидацию запроса на уровне фреймворка там, где это
   уместно.
3. Отправить прикладную команду или запрос через MediatR.
4. Сопоставить результат приложения с HTTP-ответом.

Контроллеры не должны:

- Обращаться к `DbContext` напрямую.
- Выполнять SQL-запросы.
- Реализовывать транзакции оформления заказа.
- Изменять запас напрямую.
- Содержать бизнес-процессы корзины или заказа.

API зависит от Application и Infrastructure для композиции и регистрации во
время выполнения. Он не должен становиться местом для доменных бизнес-правил.

## 3. Направление зависимостей

Основные зависимости:

```text
PS.MiniEcommerce.Domain
        ↑
PS.MiniEcommerce.Application
        ↑
PS.MiniEcommerce.Infrastructure

PS.MiniEcommerce.API
        ├── PS.MiniEcommerce.Application
        └── PS.MiniEcommerce.Infrastructure
```

Более точно:

- Domain не имеет проектных зависимостей от других проектов приложения.
- Application ссылается на Domain.
- Infrastructure ссылается на Application и Domain.
- API ссылается на Application и Infrastructure.
- Модульные тесты могут ссылаться на проекты, поведение которых они проверяют.
- Интеграционные тесты проверяют API и инфраструктуру в связке с SQL Server.

Направление зависимостей должно сохранять независимость бизнес-правил от базы
данных и HTTP-фреймворка.

Не добавляйте проектные ссылки, создающие циклические зависимости.

## 4. Поток обработки запроса в приложении

Типичный запрос проходит следующий путь:

```text
HTTP Request
    ↓
ASP.NET Core Controller
    ↓
MediatR Command or Query
    ↓
Validation Pipeline Behavior
    ↓
Application Handler
    ↓
Application Interface
    ↓
Infrastructure Implementation
    ↓
SQL Server
```

Результат возвращается через обработчик и контроллер и преобразуется в
HTTP-ответ.

Точный порядок конвейера и сопоставление исключений должны быть настроены
согласованно с контрактом API.

Не каждый запрос требует явной абстракции репозитория. Сохраняйте доступ к
данным простым там, где отдельная абстракция не добавляет существенной ценности.

## 5. Команды и запросы

Используйте разделение команд и запросов в проекте Application.

- **Команды** представляют операции, изменяющие состояние приложения.
- **Запросы** извлекают данные, не изменяя бизнес-состояние.

Примеры команд:

- `AddCartItemCommand`
- `UpdateCartItemQuantityCommand`
- `RemoveCartItemCommand`
- `CheckoutCommand`
- `CancelOrderCommand`

Примеры запросов:

- `GetProductsQuery`
- `GetProductByIdQuery`
- `GetCartQuery`
- `GetOrdersQuery`
- `GetOrderByIdQuery`

Эти имена приведены для иллюстрации. Окончательные имена и контракты
запросов/ответов могут быть скорректированы в соответствии с финальным дизайном
API.

Не вводите отдельные базы данных для чтения и записи. CQRS здесь — это шаблон
организации прикладного кода, а не распределённая архитектура.

## 6. Организация приложения

Организуйте функции приложения по сценариям использования, а не размещайте все
обработчики в одной большой папке.

Возможная структура:

```text
src/Backend/PS.MiniEcommerce/PS.MiniEcommerce.Application/
├── Products/
│   ├── Queries/
│   └── DTOs/
├── Carts/
│   ├── Commands/
│   ├── Queries/
│   └── DTOs/
├── Orders/
│   ├── Commands/
│   ├── Queries/
│   └── DTOs/
├── Abstractions/
│   └── CurrentUser/
└── Behaviors/
```

Структура может уточняться по мере реализации функций.

Не создавайте пустые папки или абстракции для гипотетических будущих функций.

## 7. Валидация

Используйте FluentValidation для валидации прикладных запросов.

Централизованное поведение конвейера MediatR должно выполнять применимые
валидаторы до обработчика.

Валидация должна различать:

- Ограничения формы запроса и входных данных.
- Валидацию бизнес-правил.
- Условия конкурентности и целостности, обеспечиваемые базой данных.

Примеры валидации входных данных:

- Количество должно быть положительным целым числом.
- Обязательные значения запроса должны присутствовать.
- Ключ идемпотентности должен соответствовать формату, определённому в
  `../DECISIONS.md`.
- Обязательный заголовок `If-Match` должен присутствовать и содержать один
  конкретный тег сущности.
- Параметры пагинации должны находиться в документированных пределах.

Примеры проверок бизнес-правил:

- Товар активен.
- Корзина не пуста при оформлении заказа.
- Запрошенное количество допустимо при текущем запасе.
- Заказ может быть отменён.

Проверки, зависящие от изменяемого состояния базы данных, должны выполняться
безопасно в рамках соответствующей транзакции и стратегии конкурентного доступа.
Одно правило FluentValidation не может гарантировать согласованность запаса.

Итоговое сопоставление ошибок валидации и бизнес-ошибок с кодами состояния HTTP
должно соответствовать `api.md`.

## 8. Текущий пользователь и принадлежность

Прикладные сценарии использования должны получать текущего пользователя через
прикладную абстракцию, например `ICurrentUser`.

Контекст аутентификации API предоставляет аутентифицированную идентичность.
Операции сохранения данных в Infrastructure и обработчики приложения не должны
доверять идентификатору пользователя, переданному в теле запроса, при
определении принадлежности.

Требования:

- Операции с корзиной применяются только к корзине текущего пользователя.
- История заказов содержит только заказы текущего пользователя.
- Сведения о заказе и отмена проверяют принадлежность.
- Запросы к заказу другого пользователя следуют утверждённому поведению при
  отсутствии ресурса.
- Эндпоинты каталога и `GET /health` являются публичными и не требуют
  аутентификации.
- Все остальные эндпоинты требуют аутентификации и отклоняют анонимные запросы.
- Механизм `X-Test-User`, предназначенный только для Development, не должен быть
  доступен в Production.

Абстракция текущего пользователя принадлежит Application. Её реализация во время
выполнения и конфигурация аутентификации подключаются через композицию API.

## 9. Сохранение данных и транзакции

EF Core — технология сохранения данных по умолчанию. Операции, специфичные для
SQL Server, могут использовать явный SQL, когда это требуется для корректности.

### 9.1 Конкурентный доступ к корзине

Изменения корзины и оформление заказа должны следовать утверждённой стратегии
блокировки, описанной в `../adr/ADR-001-cart-concurrency.md`.

Реализация должна:

- Захватывать требуемую блокировку корзины в рамках транзакции и удерживать её
  до завершения транзакции.
- Проверять переданное клиентом значение `If-Match` на соответствие текущему
  `rowversion` и предоставлять `rowversion` как `ETag` корзины.
- Не предполагать, что обычные запросы EF Core автоматически захватывают
  `UPDLOCK`.
- Обновлять строку корзины при каждом изменении содержимого корзины, в том числе
  во время оформления заказа, чтобы устаревший запрос не мог восстановить
  устаревшее содержимое корзины.

### 9.2 Согласованность запаса

Оформление заказа должно использовать атомарные условные списания запаса и
проверять количество затронутых строк, обрабатывая строки товаров в стабильном
порядке по идентификатору товара.

Снимки названия товара и цены за единицу для позиций заказа должны читаться, пока
строки товаров ещё заблокированы этими обновлениями.

Все списания запаса при оформлении заказа должны участвовать в той же
транзакции, что и создание заказа, очистка корзины и изменение версии строки
корзины.

Если какое-либо требуемое списание завершается неудачно, оформление заказа не
должно оставлять частичный заказ или частичные изменения запаса. Ответ о
недостаточном запасе формируется на основе отдельного чтения после отката
неудачной транзакции.

Отмена должна восстанавливать точные количества, записанные в заказе, и атомарно
обновлять статус заказа, используя условное обновление статуса, чтобы успешно
завершался только один одновременный запрос и восстанавливал запас.

### 9.3 Владение транзакцией

Каждый сценарий использования должен иметь чётко определённую границу
транзакции.

Оркестрация оформления заказа принадлежит слою Application: обработчик
оформления заказа определяет порядок выполнения бизнес-проверок и получения
результатов. Сама транзакция открывается, фиксируется и откатывается через узкий
интерфейс, специфичный для оформления заказа, который определён в Application и
реализован в Infrastructure, например `ICheckoutTransactionExecutor`. Эта абстракция
существует потому, что транзакции EF Core, явные блокировки SQL и условные
обновления не могут находиться в Application, а API и Infrastructure не должны
владеть бизнес-процессом. Это документированная абстракция для конкретной цели,
а не универсальный Unit of Work.

Такая организация должна удовлетворять следующим требованиям:

- Слой Application остаётся независимым от EF Core.
- Блокировки и поведение транзакций, специфичные для инфраструктуры, остаются
  явными.
- Сценарий использования не может случайно зафиксировать только часть требуемой
  бизнес-операции.
- Границы транзакций покрываются интеграционными тестами с SQL Server.

Не добавляйте универсальную абстракцию Unit of Work или универсальный репозиторий
только для обёртки `SaveChangesAsync`.

Транзакции выполняются на уровне изоляции, определённом в `../DECISIONS.md`.
В MVP взаимоблокировки не повторяются внутри процесса; запрос завершается
неудачно, а клиент повторяет его с тем же ключом идемпотентности или повторно
получает корзину.

Стратегия резервирования, ограниченного ожидания и восстановления по требованию
для идемпотентности оформления заказа должна соответствовать
`../adr/ADR-002-checkout-idempotency.md`.

## 10. Обработка ошибок

Используйте согласованную модель ошибок во всём приложении.

Ожидаемые сбои должны представляться так, чтобы API мог вернуть согласованный
ответ `ProblemDetails`.

Примеры включают:

- Недопустимые значения запроса.
- Отсутствующие товары или заказы.
- Недостаточный запас.
- Устаревшие обновления корзины.
- Недопустимое состояние оформления заказа.
- Повторное использование ключа идемпотентности с другим содержимым.
- Повторная отмена уже отменённого заказа.

Неожиданные исключения должны регистрироваться в журнале должным образом и
сопоставляться с общей ошибкой сервера без раскрытия внутренних деталей
реализации.

Не возвращайте клиентам сообщения исключений базы данных или трассировки стека.

Стабильные коды ошибок и поле расширения `ProblemDetails` определены в `api.md`.
Соглашение о URI `type` может быть окончательно установлено во время реализации,
но оно не должно вводить формат, конкурирующий с документированным контрактом.

## 11. Внедрение зависимостей и конфигурация

Композиция API отвечает за регистрацию зависимостей приложения во время
выполнения.

- Регистрировать обработчики и поведения конвейера MediatR.
- Регистрировать валидаторы FluentValidation.
- Регистрировать интерфейсы Application с их реализациями в Infrastructure.
- Настраивать EF Core с выбранным подключением к SQL Server.
- Регистрировать службы аутентификации и авторизации.
- Регистрировать схему тестовой аутентификации, предназначенную только для
  Development, исключительно в Development.
- Регистрировать проверку работоспособности, используемую `GET /health`.

Строки подключения и секреты должны передаваться через соответствующие механизмы
конфигурации и не должны попадать в систему контроля версий.

Не вводите отдельный фреймворк внедрения зависимостей.

## 12. Границы тестирования

### Модульные тесты

Используйте модульные тесты для проверки изолированного поведения приложения и
предметной области, включая:

- Валидацию входных данных.
- Доменные инварианты.
- Переходы статусов.
- Расчёты итоговой суммы заказа.
- Ожидаемые результаты бизнес-правил.
- Поведение обработчиков, не требующее реальной конкурентности базы данных.

Используйте NSubstitute, когда полезен тестовый двойник. Избегайте имитации
поставщиков запросов EF Core или использования имитаций для доказательства
поведения SQL Server.

### Интеграционные тесты

Используйте интеграционные тесты с SQL Server для проверки:

- Сопоставлений и миграций EF Core.
- Ограничений базы данных.
- Транзакций и отката.
- Блокировки корзины, валидации `If-Match` и обработки устаревших обновлений.
- Создания корзины при первом обращении в условиях одновременных первых
  запросов.
- Атомарных списаний запаса.
- Идемпотентности оформления заказа, включая ограниченное ожидание и
  восстановление по требованию.
- Одновременной отмены.
- Изоляции пользователей через API.

База данных в памяти не заменяет SQL Server, когда тест зависит от блокировок
SQL Server, rowversion, изоляции или поведения затронутых строк.

## 13. Архитектурные ограничения

Следующие правила обязательны:

1. Domain не зависит от Infrastructure или API.
2. Application не зависит от Infrastructure или API.
3. Контроллеры не содержат бизнес-процессов.
4. Infrastructure владеет сопоставлениями EF Core и поведением сохранения
   данных, специфичным для SQL Server.
5. Изменяемое состояние базы данных повторно проверяется в рамках
   соответствующих границ конкурентного доступа и транзакций.
6. Для конкурентного доступа к корзине, согласованности запаса и идемпотентности
   нельзя полагаться только на поведение клиента.
7. Без явной необходимости не вводятся универсальный репозиторий, универсальный
   Unit of Work, система доменных событий или дополнительный проект.
8. В MVP не добавляются функциональность платежей, доставки, купонов,
   микросервисов или брокеров сообщений.
