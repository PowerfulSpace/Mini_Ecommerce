# ADR-001: Стратегия конкурентного доступа к корзине и блокировок

- **Status:** Accepted, amended on 2026-10-15 (cart version transport moved to `ETag`/`If-Match`, stale-version status changed from `409` to `412`, checkout is required to change the cart row)
- **Date:** 2026-10-15

## Контекст

В MVP Mini E-commerce у пользователя не более одной корзины. Несколько запросов
могут одновременно пытаться изменить одну и ту же корзину. Оформление заказа
также читает и изменяет корзину, проверяя товары, списывая запас, создавая заказ
и очищая позиции корзины.

Без явной стратегии конкурентного доступа система может столкнуться со
следующим:

- Потерянными обновлениями корзины.
- Оформлением заказа с использованием несогласованного состояния корзины.
- Восстановлением старых позиций корзины при обновлении после оформления заказа.
- Дублирующимися или несогласованными списаниями запаса.
- Частичными бизнес-операциями при неудаче одновременных запросов.

Приложение использует SQL Server и Entity Framework Core. Стратегия должна
работать с семантикой транзакций SQL Server и не должна полагаться на то, что
LINQ-запросы EF Core неявно предоставляют конкретную подсказку блокировки строк.

## Решение

Использовать сочетание:

1. Транзакции базы данных для каждого изменения корзины и оформления заказа.
2. Явной блокировки хранимой строки корзины на время транзакции.
3. SQL Server `rowversion`, передаваемого клиентам как `ETag` корзины и
   возвращаемого через `If-Match`.
4. Атомарных условных обновлений запаса для защиты товарных остатков.
5. Согласованного порядка захвата блокировок для уменьшения взаимоблокировок.

Блокировка строки корзины и версия API служат разным целям и обе необходимы.

## Блокировка строки корзины

Каждое изменение корзины и оформление заказа должны:

1. Начинать транзакцию базы данных.
2. Захватывать блокировку обновления текущей строки корзины пользователя с
   помощью SQL Server `UPDLOCK` или эквивалентного явного механизма с требуемой
   семантикой.
3. Читать и проверять состояние корзины, удерживая блокировку.
4. Выполнять требуемые изменения.
5. Фиксировать или откатывать транзакцию.

Блокировка должна удерживаться до завершения транзакции.

Реализация не должна предполагать, что обычный LINQ-запрос EF Core
автоматически захватывает `UPDLOCK`. Следует использовать явный SQL или механизм
доступа к базе данных и задокументировать его в реализации Infrastructure.

Строка корзины должна существовать до того, как операция попытается её
заблокировать. Корзины создаются при первом обращении посредством
`GET /api/cart` и защищены уникальным ограничением на `Cart.UserId`.
Одновременная попытка создания разрешается путём перехвата нарушения уникального
ограничения и повторного чтения выигравшей строки.

## Версия корзины через ETag и If-Match

SQL Server `rowversion` корзины возвращается клиентам как HTTP `ETag` в каждом
представлении корзины. Значение — это Base64-кодирование 8-байтового
`rowversion`, всегда передаваемое как заключённый в кавычки сильный тег сущности.

Клиенты должны передавать полученное значение `ETag` в заголовке `If-Match` при
каждом изменении корзины и при оформлении заказа. Операции, требующие `If-Match`:

- `POST /api/cart/items`
- `PUT /api/cart/items/{productId}`
- `DELETE /api/cart/items/{productId}`
- `POST /api/orders`

Отмена заказа не использует `If-Match`; вместо этого она защищена условным
переходом статуса заказа.

Правила:

- Отсутствие обязательного `If-Match` возвращает `428 Precondition Required` с
  кодом `precondition_required`. Требуется один конкретный тег сущности;
  `If-Match: *` не поддерживается и отклоняется как недопустимый запрос.
- Приложение сравнивает переданное значение с текущим `rowversion`, работая в
  рамках транзакции корзины и блокировки.
- Устаревшее значение возвращает `412 Precondition Failed` с кодом ошибки
  `cart_version_conflict`. Операция не применяется и автоматически не
  повторяется для более нового состояния корзины.
- Успешное изменение корзины возвращает обновлённую корзину и её новый `ETag`.

`rowversion` — это дополнительная проверка устаревшего состояния. Она не меняет
блокировку строки корзины. Блокировка сериализует одновременные операции; версия
обнаруживает запросы, основанные на устаревшем представлении корзины.

Это изменяет прежний контракт, в котором версия была полем тела запроса с именем
`version`, а устаревшее значение возвращало `409 Conflict`. Значение `code`
`cart_version_conflict` не изменено, чтобы существующая обработка ошибок
клиентом оставалась осмысленной; изменились только способ передачи и статус
HTTP.

## Поведение при изменении корзины

Все изменения корзины должны проверять операцию полностью до фиксации изменений.

- Добавление существующего товара увеличивает его количество.
- Запрошенные количества должны быть положительными целыми числами.
- Неактивные товары нельзя добавлять или обновлять.
- Запрошенные количества не могут превышать доступный запас.
- Неудачное изменение не должно частично изменять корзину.
- Удаление неактивного товара разрешено.

Реализация должна сохранять эти правила при одновременном поступлении запросов.

## Поведение при оформлении заказа

Оформление заказа захватывает блокировку строки корзины перед чтением и проверкой
текущей корзины, но только после того, как слой идемпотентности проверил, есть ли
для переданного ключа сохранённый результат или активная попытка.

Для новой попытки оформления заказа транзакция остаётся активной, пока
приложение:

1. Проверяет переданное значение `If-Match` на соответствие текущей версии
   корзины.
2. Читает корзину и её позиции.
3. Проверяет активность товаров и запрошенные количества.
4. Списывает запас с помощью атомарных условных обновлений, захватывая строки
   товаров в стабильном порядке по `ProductId`.
5. Читает названия и цены товаров, используемые для снимков позиций заказа, пока
   строки товаров всё ещё заблокированы этими обновлениями.
6. Создаёт заказ и снимки позиций заказа.
7. Очищает позиции корзины.
8. Обновляет строку корзины, например устанавливая `UpdatedAtUtc`, чтобы её
   `rowversion` изменился.
9. Помечает запись идемпотентности завершённой в рамках успешной транзакции
   оформления заказа.
10. Фиксирует транзакцию.

Создание заказа, списание запаса, очистка корзины, изменение версии строки
корзины и успешное завершение идемпотентности должны фиксироваться атомарно.

Шаг 8 обязателен. Удаление строк `CartItem` не изменяет строку `Cart`, поэтому
без явного обновления строки корзины ранее выданный `ETag` оставался бы
действительным после оформления заказа, и устаревшее изменение могло бы успешно
примениться к опустевшей корзине.

Если проверка или обновление запаса завершается неудачно, транзакция оформления
заказа откатывается. Заказ не создаётся, списания запаса отменяются, а корзина
остаётся без изменений.

Окончательные ответы с бизнес-ошибками, включая `cart_version_conflict`,
сохраняются механизмом идемпотентности после отката неудачной транзакции
оформления заказа. Неожиданные инфраструктурные ошибки не сохраняются как
окончательные бизнес-результаты.

## Обновление корзины и оформление заказа

Изменение корзины и оформление заказа для одного и того же пользователя должны
сериализоваться блокировкой строки корзины.

### Изменение корзины захватывает блокировку первым

Изменение проверяет и применяет свои изменения, затем фиксирует транзакцию.
Оформление заказа захватывает блокировку после этого и оценивает результирующее
состояние корзины.

Оформление заказа всё равно может завершиться с `412 Precondition Failed`, если
версия, переданная клиентом, устарела. Клиент должен получить текущую корзину и
начать новую попытку оформления заказа с новым ключом идемпотентности.

### Оформление заказа захватывает блокировку первым

Оформление заказа проверяет корзину, создаёт заказ, списывает запас, очищает
позиции корзины, изменяет строку корзины и фиксирует транзакцию. Ожидающее
изменение корзины затем захватывает блокировку.

Поскольку оформление заказа изменило строку корзины, значение `If-Match`
ожидающего изменения больше не соответствует текущему `rowversion`, и изменение
завершается с `412 Precondition Failed`. Оно не должно восстанавливать позиции,
которые были в корзине до оформления заказа.

Это правило предотвращает восстановление позиций устаревшим обновлением корзины
после успешного оформления заказа.

## Конкурентность запаса

Блокировка строки корзины защищает корзину одного пользователя. Она не защищает
запас товара, общий для разных пользователей.

Списания товарных остатков должны поэтому использовать атомарные условные
обновления базы данных, которые выполняются успешно, только если товар имеет как
минимум запрошенное количество в запасе, например:

```sql
UPDATE Products
SET StockQuantity = StockQuantity - @Quantity
WHERE Id = @ProductId AND StockQuantity >= @Quantity
```

Приложение должно проверять количество затронутых строк. Неудачное условное
обновление означает, что требование к запасу не было выполнено на момент
обновления.

Все списания запаса для одного оформления заказа относятся к одной транзакции.
Если какое-либо списание завершается неудачно, вся транзакция оформления заказа
откатывается.

Ответы о недостаточном запасе идентифицируют каждый затронутый товар после
отката неудачной транзакции, используя отдельное чтение текущего запаса. Список
носит информационный характер и не означает, что запас остаётся
зарезервированным.

## Порядок блокировок и взаимоблокировки

Когда операция должна заблокировать несколько строк товаров, она должна
захватывать их в стабильном порядке, предпочтительно по `ProductId`.

MVP не повторяет взаимоблокировки автоматически внутри процесса. Транзакция
жертвы взаимоблокировки откатывается, и запрос завершается неудачно. Клиент
повторяет оформление заказа с тем же ключом идемпотентности и тем же запросом
либо повторно получает корзину перед новым изменением. Повторная попытка должна
повторно прочитать и проверить соответствующее состояние и никогда не должна
создавать отдельную попытку оформления заказа.

## Границы транзакций и изоляция

Следующие операции должны быть атомарными:

- Одно изменение корзины и обновление её версии.
- Создание заказа при оформлении, все списания запаса, очистка корзины,
  изменение версии строки корзины и успешное завершение идемпотентности.
- Отмена заказа, переход статуса и полное восстановление запаса.

MVP выполняет эти транзакции на уровне SQL Server `READ COMMITTED`, который
является уровнем по умолчанию для базы данных, и полагается на явные подсказки
`UPDLOCK`, условные обновления с проверкой затронутых строк и стабильный порядок
блокировок вместо более строгого уровня изоляции. Это рекомендация для MVP, а не
утверждение, что конкретный уровень уже реализован.

Для отмены база данных должна гарантировать, что только один одновременный
запрос может выполнить переход из `Created` в `Cancelled` и восстановить запас,
используя условное обновление, например
`UPDATE Orders SET Status = 'Cancelled' WHERE Id = @OrderId AND Status = 'Created'`.
Повторная или проигравшая попытка отмены не должна снова восстанавливать запас.

Оркестрация оформления заказа принадлежит слою Application; сама транзакция
открывается и фиксируется узкой инфраструктурной абстракцией, специфичной для
оформления заказа. См. `../architecture/architecture.md`, раздел 9.3.

## Последствия

### Преимущества

- Одновременные изменения одной корзины сериализуются.
- Устаревшие клиентские запросы обнаруживаются явно.
- Оформление заказа не может незаметно использовать устаревшее состояние
  корзины.
- Обновления корзины не могут восстанавливать позиции после оформления заказа.
- Корректность товарных остатков защищена независимо от блокировки корзины.
- Границы транзакций делают поведение отката явным.

### Компромиссы

- Требуется явный SQL или другой механизм блокировки, специфичный для базы
  данных.
- Удержание блокировки корзины на протяжении оформления заказа может увеличить
  конкуренцию между запросами, затрагивающими одного и того же пользователя.
- Длительных транзакций следует избегать.
- Взаимоблокировки остаются возможными, и о них сообщается клиенту вместо
  повторных попыток внутри процесса.
- Реализация блокировки специфична для выбранной реляционной базы данных, если
  для другой базы данных не реализована эквивалентная стратегия.
- `READ COMMITTED` требует, чтобы явная блокировка и механизмы условных
  обновлений оставались корректными; их удаление ослабило бы гарантии.

## Требования к реализации

- Держать оркестрацию транзакций на границе Infrastructure/Application,
  определённой в `../architecture/architecture.md`; не размещать код блокировки
  базы данных в контроллерах API.
- Обеспечить уникальное ограничение базы данных для связи пользователя с
  корзиной.
- Реализовать явную блокировку строки корзины в SQL Server.
- Настроить и предоставлять EF Core `rowversion` как `ETag` корзины, а также
  требовать `If-Match` при изменениях корзины и оформлении заказа.
- Возвращать `cart_version_conflict` с `412` для устаревших версий и
  `precondition_required` с `428` при отсутствии `If-Match`.
- Добиваться, чтобы успешное оформление заказа изменяло строку корзины, делая
  предыдущий `ETag` недействительным.
- Использовать атомарные условные обновления запаса и проверять количество
  затронутых строк.
- Согласовывать границы транзакций оформления заказа и отмены с этим ADR.
- Добавить интеграционные тесты с использованием SQL Server для одновременных
  обновлений корзины, гонок оформления заказа, устаревшего `ETag` после
  оформления, конкуренции за запас и одновременной отмены.
