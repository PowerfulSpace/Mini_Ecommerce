# Обзор проекта

## 1. Название проекта

**Mini E-commerce**

## 2. Назначение проекта

Mini E-commerce — учебное full-stack-приложение, моделирующее основной рабочий процесс небольшого интернет-магазина.

Проект предназначен для отработки backend-разработки на .NET и работы с реляционными базами данных, с особым вниманием к управлению транзакциями, конкурентным операциям, согласованности данных и надёжным бизнес-процессам.

Приложение будет включать backend API и frontend-клиент. Разработка начнётся с backend. Frontend будет реализован после того, как будут определены основная функциональность и контракты backend.

Проект спроектирован как модульное монолитное приложение. Микросервисы и распределённая инфраструктура находятся вне рамок MVP.

## 3. Цели обучения

Проект должен дать практический опыт по следующим темам.

### Архитектура backend

- Применение Clean Architecture без излишних абстракций.
- Разделение доменной логики, прикладных сценариев использования, инфраструктуры и HTTP-представления.
- Организация функциональности приложения по функциональным областям.
- Реализация команд и запросов с помощью MediatR.
- Централизованная валидация запросов с помощью FluentValidation и поведения конвейера MediatR.

### Хранение данных

- Проектирование реляционной модели данных.
- Использование Microsoft SQL Server и Entity Framework Core.
- Управление изменениями схемы через миграции базы данных.
- Поддержание целостности данных через ограничения базы данных и транзакции.

### Конкурентность и согласованность

- Предотвращение конфликтующих обновлений корзины пользователя.
- Обработка одновременных покупок ограниченного запаса.
- Атомарное списание запаса.
- Обеспечение того, что оформление заказа либо завершается полностью, либо не оставляет частичных бизнес-изменений.
- Предотвращение дублирования заказов при повторных запросах на оформление.
- Обеспечение того, что одновременные запросы на отмену не могут восстановить запас более одного раза.

### Тестирование

- Написание модульных тестов для бизнес-правил и поведения приложения.
- Написание интеграционных тестов с реальной базой данных SQL Server.
- Тестирование границ транзакций, конкурентности, идемпотентности и изоляции пользовательских данных.
- Проверка того, что важные сценарии сбоев не оставляют несогласованных данных.

### Frontend

- Создание приложения на Vue 3 с TypeScript и Vite.
- Управление состоянием на стороне клиента с помощью Pinia.
- Интеграция frontend с backend API.
- Обработка ошибок валидации, бизнес-конфликтов и состояний загрузки.

## 4. Целевое приложение

Приложение представляет собой небольшой интернет-магазин с простым процессом покупки:

1. Пользователь просматривает активный каталог товаров.
2. Пользователь добавляет товары в личную корзину.
3. Пользователь изменяет количество или удаляет товары из корзины.
4. Пользователь отправляет корзину на оформление, чтобы создать заказ.
5. Система проверяет наличие товаров и списывает запас.
6. Пользователь просматривает историю своих заказов.
7. Пользователь может отменить заказ, соответствующий условиям отмены.
8. Система восстанавливает запас, связанный с успешно отменённым заказом.

Приложение должно сохранять согласованность данных при сбоях операций или их одновременном выполнении.

## 5. Объём MVP

### Включено

- Тестовая аутентификация, доступная только в среде разработки.
- Два предварительно созданных тестовых пользователя для сценариев изоляции и конкурентности.
- Каталог товаров, доступный только для чтения без аутентификации.
- Активация и деактивация товаров, представленные в домене и базе данных.
- Пользовательские корзины, создаваемые при первом обращении к корзине.
- Создание позиций корзины, изменение количества и удаление.
- Проверка наличия запаса.
- Создание заказа и снимки позиций заказа.
- История заказов и сведения о заказе.
- Отмена заказа и восстановление запаса.
- Транзакционное оформление заказа.
- Защита от одновременных изменений корзины.
- Атомарное списание запаса.
- Идемпотентность оформления заказа через `Idempotency-Key`.
- Согласованные HTTP-ответы об ошибках с использованием `ProblemDetails`.
- Модульные тесты и интеграционные тесты с SQL Server.
- Frontend на Vue 3 после того, как backend будет реализован.

### Явно исключено

MVP не включает:

- Онлайн-платежи или интеграции с платёжными провайдерами.
- Доставка, отслеживание доставки или процессы выполнения заказов.
- Купоны, скидки или промоакции.
- Административные эндпоинты для управления товарами или административный интерфейс.
- Регистрация клиентов, восстановление пароля, OAuth или вход через социальные сети.
- Сложная ролевая авторизация.
- Микросервисы или распределённая инфраструктура приложения.
- Брокеры сообщений или потоковая обработка событий.
- Налоги, стоимость доставки или конвертация валют.
- Готовая к промышленной эксплуатации система управления идентификацией.

## 7. Архитектурное направление

Backend будет организован в виде четырёх проектов в `src/Backend/PS.MiniEcommerce/`:

- `PS.MiniEcommerce.Domain`
- `PS.MiniEcommerce.Application`
- `PS.MiniEcommerce.Infrastructure`
- `PS.MiniEcommerce.API`

Файл решения — `src/Backend/PS.MiniEcommerce/PS.MiniEcommerce.slnx`. Он использует формат `.slnx` и остаётся вложенным в каталог backend, а не в корне репозитория.

Префикс `PS.` используется намеренно и сохраняется в именах проектов, пространствах имён и путях. Отдельный проект `Common` не входит в MVP.

Frontend будет располагаться в `src/Frontend/`.

Модульные и интеграционные тесты будут располагаться в `tests/` в проектах `PS.MiniEcommerce.UnitTests` и `PS.MiniEcommerce.IntegrationTests`.

Слой Domain не должен зависеть от инфраструктуры или фреймворков представления. Прикладные сценарии использования будут зависеть от абстракций там, где это уместно, а Infrastructure будет предоставлять реализации для сохранения данных и других технических задач.

Проект будет избегать обобщённых репозиториев, ненужных общих проектов, спекулятивных абстракций и преждевременной архитектурной сложности.

Подробные зоны ответственности слоёв и правила зависимостей определены в `architecture/architecture.md`. Решения об именовании, расположении решения и инструментах сборки зафиксированы в `DECISIONS.md`.

## 8. Ключевые инженерные задачи

Основные инженерные задачи проекта — не количество эндпоинтов, а корректность переходов состояний и операций с базой данных.

### Конкурентность корзины

Одновременные обновления корзины и оформление заказа не должны молча перезаписывать более новое состояние или восстанавливать позиции корзины после оформления заказа.

### Согласованность запаса

Запас никогда не должен списываться сверх доступного количества. Неудачное оформление заказа не должно создавать заказ, частично списывать запас или очищать корзину.

### Транзакционная отмена

Отмена заказа и восстановление запаса должны быть атомарными. Одновременные попытки отмены не должны восстанавливать один и тот же запас более одного раза.

### Идемпотентность оформления заказа

Повторные запросы с одним и тем же ключом идемпотентности не должны создавать дублирующиеся заказы. Повторное использование ключа с другим телом запроса должно быть отклонено.

### Изоляция пользователей

Пользователи должны иметь доступ только к своим корзинам и заказам. API должен определять идентичность пользователя из контекста аутентифицированного запроса, а не доверять идентификатору пользователя, переданному клиентом.

Эти аспекты поведения будут подробно определены в `SPEC.md`, `DOMAIN.md` и соответствующих Architecture Decision Records.

## 9. Критерии успеха

Проект будет считаться успешным, когда:

- Решение соответствует утверждённой структуре и архитектуре проекта.
- Backend можно настроить и запустить с SQL Server.
- Миграции базы данных успешно применяются.
- Механизм тестовой аутентификации, используемый в разработке, недоступен в Production.
- Предварительно созданных тестовых пользователей можно использовать для проверки изоляции данных.
- Сценарии работы с каталогом, корзиной, оформлением заказа, историей заказов и отменой функционируют в соответствии со спецификацией.
- Одновременные операции сохраняют требуемые инварианты.
- Повторные запросы на оформление заказа не создают дублирующиеся заказы.
- Неудачные бизнес-операции не оставляют частичных изменений.
- Автоматизированные модульные и интеграционные тесты охватывают критические сценарии.
- Frontend может использовать задокументированный API для выполнения основного процесса покупки.
- Инструкции по установке, настройке и тестированию задокументированы.

## 10. Стратегия разработки

Проект будет разрабатываться поэтапно.

Начальная работа — документация и спецификация. Реализация приложения не должна начинаться до тех пор, пока документация не будет подготовлена и проверена.

После утверждения документации разработка будет продвигаться по согласованной дорожной карте, начиная с основы backend и затем охватывая основной процесс покупки, тестирование и интеграцию frontend.

Каждый этап должен иметь явный объём и критерии приёмки. Будущие этапы не должны реализовываться преждевременно.

## 11. Ограничения проекта

Проект отдаёт приоритет корректности, ясности и образовательной ценности, а не количеству функций.

Варианты реализации должны быть понятными, тестируемыми и подходящими для небольшого приложения.

Инфраструктура распределённых систем промышленного уровня не является целью. Однако транзакции базы данных, обработка конкурентности, идемпотентность, обработка ошибок и автоматизированное тестирование должны рассматриваться как реальные инженерные требования.

Любое существенное изменение согласованного объёма или архитектуры должно быть обсуждено и утверждено до реализации.
