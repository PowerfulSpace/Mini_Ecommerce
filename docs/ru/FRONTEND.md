# Спецификация фронтенда

## 1. Назначение

Этот документ определяет объём фронтенда, выбор технологий, структуру
пользовательского интерфейса и принципы интеграции для MVP Mini E-commerce.

Фронтенд будет реализован после того, как контракт backend API и основное
поведение backend станут достаточно стабильными.

Фронтенд должен оставаться простым и сосредоточенным на основном процессе
покупки. Он не должен вводить функциональность за пределами утверждённого
объёма MVP.

## 2. Технологический стек

Планируемый стек фронтенда:

- Vue 3
- TypeScript
- Vite
- Pinia для общего состояния приложения
- Vue Router для навигации на стороне клиента
- Нативный Fetch API или небольшая абстракция HTTP-клиента для запросов к backend

Точные версии зависимостей будут выбраны при начале реализации фронтенда.

Не вводите крупный UI-фреймворк, библиотеку управления состоянием или
дополнительную абстракцию без конкретной необходимости.

## 3. Цели приложения

Фронтенд должен позволять пользователю:

1. Просматривать активный каталог товаров.
2. Просматривать сведения о товаре.
3. Добавлять товары в корзину.
4. Изменять количества в корзине или удалять позиции.
5. Видеть недоступные товары и ошибки, связанные с запасом.
6. Завершать оформление заказа.
7. Просматривать историю заказов и сведения о заказе.
8. Отменять подходящий для отмены заказ.
9. Понимать состояния загрузки, пустые состояния, ошибки валидации и конфликты.

Приложение должно делать последствия действия понятными, особенно когда
backend отклоняет операцию из-за изменений запаса или одновременных запросов.

## 4. Аутентификация для разработки

Во время локальной разработки backend поддерживает тестовые идентичности
`alice` и `bob` через заголовок запроса `X-Test-User`, доступный только в
Development.

Фронтенд должен предоставлять простой способ выбора одной из этих тестовых
идентичностей только для разработки.

Выбранная идентичность должна включаться в запросы, требующие аутентификации.

Требования:

- Селектор идентичности для разработки не должен рассматриваться как
  аутентификация для production.
- Не реализуйте регистрацию клиентов, пароли или собственную систему
  аутентификации.
- Не отправляйте произвольные идентификаторы пользователей в телах запросов
  для выбора принадлежности корзины или заказа.
- Не включайте тестовый механизм аутентификации в production-сборку или
  production-конфигурацию.
- Переключение идентичностей должно приводить к повторной загрузке данных,
  специфичных для пользователя, чтобы корзина и заказы Alice никогда не
  отображались как принадлежащие Bob.

Точная реализация селектора идентичности для разработки будет определена при
настройке фронтенда.

## 5. Маршруты и экраны

Планируются следующие маршруты. Точные шаблоны URL могут быть скорректированы
при реализации при условии, что навигация остаётся понятной и согласованной.

| Маршрут | Экран | Назначение |
|---|---|---|
| `/` | Каталог товаров | Просмотр активных товаров |
| `/products/:id` | Сведения о товаре | Просмотр информации о товаре |
| `/cart` | Корзина | Просмотр и изменение позиций корзины |
| `/orders` | История заказов | Просмотр заказов текущего пользователя |
| `/orders/:id` | Сведения о заказе | Просмотр заказа и его позиций |

Отдельная страница оформления заказа необязательна. Оформление заказа может
запускаться из корзины, если это обеспечивает более простой пользовательский
опыт.

Успешное оформление заказа должно приводить к переходу на страницу сведений о
созданном заказе или на другой явно обозначенный экран подтверждения заказа.

## 6. Каталог товаров

Экран каталога должен отображать активные товары, возвращаемые backend.

Каждая запись товара должна отображать, где это доступно:

- Название товара
- Краткое описание
- Текущую цену в USD
- Информацию о доступности или запасе, когда она предоставляется API
- Действие для открытия сведений о товаре
- Действие для добавления товара в корзину

Требования:

- Не вычисляйте и не придумывайте доступность запаса на клиенте.
- Не предполагайте, что товар остаётся доступным после получения ответа
  каталога.
- Отключайте явно некорректные взаимодействия, где это уместно, но полагайтесь
  на backend как на окончательный источник истины.
- Отображайте информативное пустое состояние, когда активные товары не
  возвращены.
- Отображайте состояния загрузки и ошибки запроса.
- Каталог является публичным, и его следует запрашивать без заголовка
  аутентификации.
- Список товаров разбивается на страницы. Загружайте страницы по требованию и
  не запрашивайте размер страницы выше документированного максимума.

## 7. Сведения о товаре

Экран сведений о товаре должен отображать доступную информацию о товаре и
предоставлять действие для добавления его в корзину.

Если товар невозможно получить, отобразите состояние отсутствия или
недоступности.

Не реализуйте создание, редактирование, деактивацию или удаление товаров во
фронтенде MVP.

## 8. Корзина

Экран корзины должен отображать постоянную корзину текущего пользователя.

Для каждой позиции корзины отображайте:

- Название товара
- Текущую цену товара, когда она доступна
- Запрошенное количество
- Сумму по позиции, когда доступно достаточно информации
- Статус доступности
- Действие обновления количества
- Действие удаления

Также отображайте сумму корзины, когда её можно вычислить из возвращённых
данных.

### 8.1 Поведение корзины

- Первый запрос `GET /api/cart` для пользователя создаёт корзину на сервере.
  Расценивайте `404` с кодом `cart_not_found` при изменении как сигнал, что
  корзину необходимо сначала получить.
- Сохраняйте `ETag`, возвращаемый с каждым ответом корзины, и отправляйте его
  обратно через заголовок `If-Match` при каждом изменении корзины и при
  оформлении заказа. Не помещайте поле версии в тела запросов.
- Добавление существующего товара подчиняется правилу backend, согласно
  которому его количество увеличивается.
- Количество должно быть положительным целым числом.
- Удаление позиции должно использовать отдельную операцию удаления, а не
  отправку нулевого количества. Запрос удаления не имеет тела.
- Фронтенд не должен молча уменьшать количество, чтобы уложиться в доступный
  запас.
- Если backend отклоняет обновление количества, сохраните или перезагрузите
  авторитетное состояние сервера и объясните причину сбоя.
- Если корзина пуста, отобразите понятное пустое состояние и ссылку на каталог.
- Неактивный товар может оставаться в корзине, но должен обозначаться как
  недоступный и не должен представляться как доступный для покупки.
- Неудачное оформление заказа не должно приводить к тому, что фронтенд очищает
  корзину.

### 8.2 Конкурентные операции с корзиной

Backend отклоняет устаревшую операцию с корзиной с `412 Precondition Failed` и
кодом `cart_version_conflict`, а отсутствующий `If-Match` — с
`428 Precondition Required` и кодом `precondition_required`.

Когда это происходит:

1. Объясните, что корзина изменилась или предварительное условие отсутствовало.
2. Перезагрузите корзину из backend, чтобы получить текущий `ETag`.
3. Отобразите текущее состояние сервера.
4. Не повторяйте автоматически устаревшее изменение, не получив требуемый
   текущий `ETag`.

Клиент не должен предполагать, что локально кэшированная корзина или `ETag`
являются авторитетными.

## 9. Оформление заказа

Оформление заказа запускается из корзины.

Перед отправкой запроса фронтенд должен:

- Убедиться, что корзина содержит позиции.
- Предотвратить случайные дублирующие отправки, пока запрос выполняется.
- Сгенерировать ключ идемпотентности для попытки оформления заказа, используя
  документированный формат ключа.
- Сохранять этот ключ при повторной попытке того же действия.
- Отправлять текущий `ETag` корзины через заголовок `If-Match`.

### 9.1 Поведение идемпотентности

Backend требует заголовок `Idempotency-Key` и заголовок `If-Match` для
оформления заказа.

Фронтенд должен следовать этим правилам:

- Повторная попытка того же действия оформления заказа должна использовать тот
  же ключ и то же значение `If-Match`.
- Действительно новая попытка должна использовать новый ключ.
- Не генерируйте новый ключ только потому, что запрос завершился по тайм-ауту
  или ответ был потерян.
- Не повторяйте оформление заказа автоматически с новым ключом, когда результат
  предыдущего запроса неизвестен.
- Если backend возвращает `503` с кодом `idempotency_in_progress`, подождите
  немного и повторите тот же запрос с тем же ключом и тем же значением
  `If-Match`.
- После того как backend сохранил окончательную бизнес-ошибку для ключа, новая
  попытка требует нового ключа и свежего `ETag` корзины. Повторное использование
  старого ключа лишь воспроизводит сохранённую ошибку.
- Как только успешный заказ подтверждён, перейдите к этому заказу.

Точный механизм сохранения на стороне клиента для незавершённого ключа
идемпотентности будет выбран при реализации. Он должен поддерживать безопасное
поведение при повторных попытках без создания второго заказа.

### 9.2 Результаты оформления заказа

При успехе отображайте подтверждение заказа и соответствующую информацию о
заказе.

При нарушении бизнес-правила:

- Отображайте ошибку, возвращённую backend.
- Сохраняйте корзину.
- Перезагружайте авторитетную информацию о корзине или товаре, где это уместно,
  включая текущий `ETag`.
- Ясно давайте понять, когда пользователю нужно просмотреть корзину перед новой
  попыткой, и генерируйте новый ключ идемпотентности для этой новой попытки.

Не рассматривайте сетевой сбой, неожиданную ошибку сервера или ответ `503`
`idempotency_in_progress` как доказательство того, что оформление заказа не
удалось.

## 10. Заказы

### 10.1 История заказов

Экран истории заказов должен отображать заказы текущего пользователя для
текущей страницы. Загружайте дальнейшие страницы по требованию и соблюдайте
документированный максимальный размер страницы.

Где это возвращается API, отображайте:

- Идентификатор заказа
- Время создания
- Статус
- Общую сумму

Пустая история должна иметь информативное пустое состояние.

### 10.2 Сведения о заказе

Экран сведений о заказе должен отображать:

- Идентификатор заказа
- Время создания
- Текущий статус
- Позиции заказа
- Названия товаров, зафиксированные при оформлении заказа
- Цены за единицу, зафиксированные при оформлении заказа
- Количества
- Общую сумму

Сведения о заказе должны использовать сохранённый снимок заказа, возвращаемый
backend. Они не должны подменять исторические значения заказа текущими ценами
или названиями из каталога.

### 10.3 Отмена

Заказ со статусом `Created` может быть отменён в соответствии с контрактом
backend.

Фронтенд должен:

- Показывать действие отмены только когда это уместно.
- Запрашивать подтверждение перед отменой.
- Отображать обновлённый статус заказа после успеха.
- Объяснять конфликты, если заказ больше нельзя отменить.
- Обновлять сведения о заказе после конфликта, когда это уместно.

Отменённый заказ не должен представляться как успешный активный заказ.

## 11. Интеграция с API

Все бизнес-операции должны выполняться через backend API.

Фронтенд не должен подключаться напрямую к SQL Server или воспроизводить
бизнес-правила backend в качестве источника истины.

Используйте небольшой слой API-клиента для централизации:

- Конфигурации базового URL
- Построения запросов
- Сериализации и десериализации JSON
- Заголовков аутентификации для разработки
- Заголовков идемпотентности для оформления заказа
- Обработки HTTP-ошибок
- Разбора `ProblemDetails`

Держите логику транспорта API отдельно от компонентов страниц.

Используйте типы TypeScript для контрактов запросов и ответов API. Эти типы
должны отражать утверждённый контракт backend API, а не предположительные поля.

Не придумывайте окончательные пути эндпоинтов, свойства запросов, свойства
ответов или коды ошибок, когда контракт backend ещё не зафиксирован.

## 12. Управление состоянием

Используйте Pinia для общего состояния, когда оно действительно необходимо,
например:

- Текущая идентичность для разработки
- Состояние корзины
- Общий статус запроса или другое состояние, общее для экранов, если это
  оправдано

Не помещайте локальное состояние каждого компонента в Pinia.

Backend остаётся авторитетным источником для товаров, содержимого корзины,
запаса, статуса заказов и сумм заказов.

После изменений обновляйте общее состояние из ответа сервера или перезагружайте
затронутый ресурс.

Избегайте оптимистичных обновлений для операций, где конкурентность или
корректность запаса могут сделать отображаемый результат вводящим в
заблуждение.

## 13. Обработка ошибок и обратная связь с пользователем

Фронтенд должен различать:

- Ошибки валидации, включая недопустимый ключ идемпотентности или параметры
  запроса
- Ответы об отсутствии, включая `cart_not_found`
- Бизнес-конфликты, включая недостаточный запас
- Устаревшие версии корзины, сообщаемые как `412 Precondition Failed`
- Отсутствующие предварительные условия, сообщаемые как
  `428 Precondition Required`
- Временные состояния оформления заказа, сообщаемые как
  `503 Service Unavailable`
- Сбои аутентификации
- Сетевые сбои
- Неожиданные ошибки сервера
- Результаты оформления заказа, которые остаются неизвестными

Используйте ответ `ProblemDetails` от backend, когда он доступен.

Не отображайте пользователям необработанные трассировки стека, ошибки базы
данных или внутренние детали исключений.

Сообщения должны объяснять, что произошло, и, где возможно, что пользователь
может сделать дальше.

Не предполагайте, что все ответы `409 Conflict` имеют одинаковое значение.
Используйте стабильные коды ошибок backend, как только они будут определены.

## 14. Визуальный дизайн и доступность

Интерфейс должен быть чистым, читаемым и адаптивным.

Требования:

- Поддерживать макеты для настольных и мобильных устройств.
- Использовать семантические элементы HTML.
- Обеспечивать наличие доступных подписей у элементов форм.
- Обеспечивать видимые индикаторы фокуса и взаимодействия, доступные с
  клавиатуры.
- Делать состояния загрузки, ошибки, пустоты и успеха различимыми.
- Форматировать суммы в USD единообразно.
- Избегать ненужных анимаций и сложных визуальных эффектов.

Отдельная дизайн-система для MVP не требуется.

## 15. Тестирование

Объём и инструменты тестирования фронтенда будут выбраны при начале реализации.

Как минимум проверяйте следующее поведение вручную или с помощью автоматических
тестов:

- Загрузку каталога, разбиение на страницы и пустые состояния
- Добавление, обновление и удаление позиций корзины с текущим `ETag`
- Обработку ошибок запаса и валидации
- Обработку конфликтов устаревшей корзины и отсутствующего `If-Match`
- Успешное оформление заказа
- Повторную попытку оформления заказа с тем же ключом идемпотентности
- Повторную попытку после `503` с кодом `idempotency_in_progress`
- Генерацию нового ключа после сохранённой окончательной бизнес-ошибки
- Обработку неизвестного результата оформления заказа
- Отображение истории заказов и снимков заказов
- Отмену подходящего для отмены заказа
- Переключение между Alice и Bob без утечки состояния, специфичного для
  пользователя

Интеграционные тесты backend по-прежнему отвечают за подтверждение транзакций
базы данных, согласованности запаса, конкурентности и идемпотентности.

## 16. Вне объёма

Фронтенд MVP не включает:

- Обработку платежей
- Управление доставкой или отгрузкой
- Купоны или скидки
- Регистрацию клиентов или управление production-идентичностями
- Администрирование товаров
- Обновления запаса в реальном времени
- Оформление заказа в офлайн-режиме
- Сложную дизайн-систему
- Отдельный административный интерфейс

## 17. Определённые детали реализации

Пути эндпоинтов, схемы DTO, коды ошибок и механизм предварительных условий
корзины определены в `architecture/api.md` и не являются открытыми вопросами.

Детали, оставленные открытыми для реализации фронтенда, были определены на
этапах 9–10. Они не меняют контракт backend.

### 17.1 Незавершённый ключ идемпотентности оформления заказа

- Незавершённый ключ сохраняется в `sessionStorage` под именем
  `mini-ecommerce:checkout-key` (`src/utils/idempotency.ts`, `KEY_STORAGE_NAME`).
  `sessionStorage` используется потому, что ключ привязан к одной вкладке/сессии
  браузера и не должен просачиваться между вкладками.
- Когда `sessionStorage` недоступен (SSR, приватный режим, отключённое
  хранилище), резервный вариант в памяти сохраняет поведение при повторных
  попытках на протяжении времени жизни страницы.
- Ключ генерируется как UUID v4, что соответствует документированному формату в
  `DECISIONS.md` §10. Он создаётся при первой попытке оформления заказа и
  повторно используется для повторов того же действия. Он очищается только
  после подтверждённого успеха или сохранённой окончательной бизнес-ошибки.

### 17.2 Устаревшее или отсутствующее предварительное условие корзины (`412` / `428`)

- `412 cart_version_conflict` или `428 precondition_required` рассматривается как
  конфликт версий: корзина повторно загружается для получения текущего `ETag` и
  авторитетного состояния сервера, и конфликт выводится пользователю. Устаревшее
  изменение никогда не воспроизводится автоматически (`src/stores/cart.ts`,
  `runMutation`).
- Оформление заказа обрабатывает те же коды как окончательные бизнес-ошибки:
  ключ идемпотентности расходуется, корзина повторно загружается, и пользователь
  должен начать новую попытку с новым ключом (`src/stores/checkout.ts`).

### 17.3 `ETag` корзины

- `ETag` хранится в `cartStore` (`src/stores/cart.ts`). Он обновляется из каждого
  ответа корзины (чтение или изменение) и отправляется обратно через `If-Match`
  при каждом изменении корзины и при оформлении заказа. Поле версии не
  помещается в тела запросов.
- Сервис корзины (`src/services/api/cart.ts`) отклоняет ответ корзины, который
  не содержит `ETag`, потому что отсутствие версии сделало бы последующие
  изменения небезопасными.

### 17.4 Селектор идентичности для разработки

- Селектор находится в `src/components/layout/Header.vue` и отображается только
  когда `import.meta.env.DEV` истинно, поэтому он отсутствует в
  production-сборке.
- Выбранная идентичность хранится в `localStorage` (`mini-ecommerce:test-user`)
  и добавляется как заголовок `X-Test-User` посредством `apiClient`. Публичные
  запросы каталога отказываются от него через `omitTestUserHeader`, поэтому
  отправляются без заголовка идентичности.
- Переключение идентичности сбрасывает хранилища, привязанные к пользователю, и
  увеличивает `identityVersion`. Экраны, привязанные к пользователю, используют
  `useUserScopedFetch` для повторной загрузки на месте, поэтому пользователь
  остаётся на текущем маршруте. Публичные хранилища каталога и товаров не
  сбрасываются при смене идентичности.

### 17.5 Подтверждение заказа

- После успешного оформления заказа клиент переходит на маршрут подтверждения
  заказа, представление которого (`OrderConfirmationView.vue`) немедленно
  перенаправляет на `/orders/:id`. Экран сведений о заказе является единственным
  источником истины; экран подтверждения не дублирует его интерфейс.

### 17.6 Инструменты тестирования

- Тесты фронтенда используют Vitest с `@vue/test-utils` и `happy-dom`. Версии
  зависимостей фиксируются в `package.json`.
